# 開発イシューを作成する

目的は、別のAIが会話の履歴なしで実装・検証できるイシューを残すこと。日本語で書く。

## 調査と分割

- ルートのAGENTS.md、README.md、docs/以下、関連実装・テスト、git statusとgit diffを読む。設計案と現在の実装を区別し、既存の未コミット変更を保持する。
- 接続済みGitHubツールを優先し、なければ利用可能なgh CLIで対象リポジトリと既存のopen/closedイシュー・関連PRを確認する。ローカル案も検索し、重複する仕事は再作成せず既存を案内する。接続できなければ重複確認未実施と記す。
- AGENTS.mdの実装優先順位とdocs/TASKS.mdに沿い、今回依頼された範囲だけを分割する。1件は独立にレビュー・検証可能な成果にし、変更対象ファイルの数だけで細分化しない。
- 依存を先行イシューのURLまたはローカルIDで明示する。未確定の認証・仕様は仮定と区別し、実装不能なら調査課題に分ける。現在のAPI仕様が必要な箇所は公式資料で確認する。

## 各イシューの本文

次の情報を記載する。不要な節は省いてよいが、受け入れ条件と検証方法は省かない。

```markdown
## 背景・目的
現状の問題と、完了時にユーザーができること。根拠となる仕様・実装のパス。

## 対象範囲
変更する動作と関連箇所。実装方法は確定事項と案を分ける。

## 対象外
今回には含めない隣接機能。

## 受け入れ条件
- [ ] 操作・入力に対する観測可能な結果
- [ ] 必要な失敗時の動作・既存動作の維持

## 検証方法
受け入れ条件に対応する自動検証と手動操作。公開環境・実機・認証が必要なら明記。

## 優先度・依存関係
優先度と理由、先行イシュー、必要なアカウント・設定。なければ「なし」。
```

完了条件を「実装する」「テストする」だけにしない。例えばAI編集なら、提案の試聴で現在曲が変化しないことや古い応答が適用されないことを検証可能に書く。秘密情報や写真そのものは本文に含めない。

## 保存と引き継ぎ

- GitHub投稿を依頼されていて対象リポジトリが特定できる場合に投稿する。単なる案の依頼では投稿しない。ラベル・担当者・マイルストーンは既存運用または明示された指定に合わせる。
- 接続・認証不足や下書き指定ならdocs/issues/に未使用のLOCAL-001等をIDとしてMarkdown保存する。タイトルと上記本文を含め、GitHub未投稿と明記する。番号をGitHub番号として扱わない。
- 複数件を投稿する際は先行分のURLを後続本文に反映する。投稿結果が不明なら再投稿前に一覧で照合し、重複を防ぐ。認証・権限エラーを繰り返さず、残りは下書きとして残す。
- docs/TASKS.mdに作成済みイシューへのリンクを残す。イシュー作成だけで製品機能を実装済みにしない。
- 最後にタイトル、URLまたはローカルパス、推奨着手順、未解決事項を報告する。実装は依頼範囲に含まれる場合のみ続ける。
